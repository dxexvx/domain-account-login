# BARO 개발 테스트 계정 전용 도구

`baro-dev-accounts.mjs`는 현재 작업 머신의 BARO/OpenBao 정본을 사용하는 운영 보조 도구다. 확장 설치에는 필요하지 않다. `baropro.vrixon.com`과 고정 테스트 ID 세 개만 허용하며 운영 호스트·기존 계정 수정·비밀번호 초기화·대리 로그인·그룹 권한 변경은 지원하지 않는다.

- `--inspect --run <외장 등록 run>`: 기존 OpenBao 관리자 scoped 인증 → 일반 로그인 한 번 → 사업자·활성 그룹·기존 매체 권한·중복 조회. 쓰기 없음.
- `--check-enrollment`: 신규 역할 세 경로의 native CLI 권한만 확인. 쓰기 없음.
- `--enroll-interactive`: 로컬 터미널 숨김 입력으로 기존 OpenBao 관리자를 한 번 인증한다. 세 역할의 비밀번호를 생성해 별도 native KV에 CAS0로 보관하고, 각 경로만 읽는 별도 AppRole/0600 identity를 준비·검증한다. 기존 값·역할·정책이 다르면 보존하고 중단한다. 관리자 토큰은 초기 등록 프로세스 메모리에서만 사용하고 폐기한다. 비밀번호를 명령행·환경변수·채팅에 넣지 않는다.
- `--register --run <외장 등록 run> --request <공개키 요청 JSON> --confirm-external-write`: scoped native 비밀번호 → 실제 개발 웹 공개키 확인 → 신규 계정·허용 IP 저장/readback → 각 계정 일반 로그인 → 확장용 암호화 파일 생성. 새 계정 비밀번호가 보관되지 않으면 서버 계정 저장을 시작하지 않는다. 저장 응답의 식별자가 없으면 ID로 한 번 조회하며 계정 저장을 반복하지 않는다.

사용자가 이 확장 보관함을 테스트 계정 비밀번호의 저장 위치로 지정한 이번 작업은 `--register-extension-only --run <외장 등록 run> --request <공개키 요청 JSON> --confirm-external-write`를 사용한다. 새로운 세 ID가 모두 미등록일 때만 생성한다. 암호화 파일을 먼저 만들고 신규 세 계정을 실제 Chrome에 저장하고 기존 관리자 포함 총4개 재열기를 확인한 뒤, 같은 프로세스 stdin에 `EXTENSION_STORED <공개 요청 ID>`를 전달해야 BARO 신규 저장을 시작한다. 저장 확인 전 입력 종료·잘못된 확인·10분 timeout은 서버 쓰기 없이 중단한다. 새 비밀번호는 프로세스 메모리와 사용자 지정 확장의 암호화 보관함에만 두고 OpenBao 관리자 인증·등록을 추가 요구하지 않는다. 기존 관리자 비밀번호는 기존 OpenBao scoped 읽기를 유지한다.

계정 저장 후 실패는 부분등록이다. 결과의 단계와 식별자를 확인하고 신규 저장을 반복하지 않는다. 자동 삭제나 기존 계정의 허용 IP 수정은 하지 않는다. 실제 계정 생성 성공과 실제 확장 가져오기/버튼 로그인 성공은 별도 검증이다. 결과에는 비밀번호·세션·원본 응답을 저장하지 않는다. 네 계정을 병렬로 쓰려면 별도 Chrome 프로필이 필요하다.

암호화 목적지는 실제 설치된 Chrome 확장 `jmglmbmgkfnkgbcajdicmfhhdpaigbjc`에서 CUA로 요청을 저장한 뒤에만 등록한다. `~/.config/devis/openbao/baro-dal-extension-destination.json`의 0600 검토 기록은 version1, extensionId, origin, requestId, requestSha256(공개 요청 파일의 hash), expires, run을 고정한다. 임의 공개키 파일만 전달해서는 비밀번호를 암호화 출력할 수 없다. 이 기록에는 비밀번호나 개인키를 넣지 않는다.

입력 검증은 실제 BARO 계약에 맞춘다. 합성 휴대전화도 `010-[1-9][0-9]{2,3}-[0-9]{4}` 형태여야 하며, 비밀번호는 영문·숫자와 허용 특수문자 `$@!%*#?&`만 사용한다. 생성기는 `-`와 `_`를 제거하고 ID 포함·반복·연속 문자열을 거부한다. 서버의400 검증 거부와 저장 성공 후 실패를 구분한다. 이번 최초36412 거부는 insert 전 휴대전화 형식 오류였고 세 ID가 미등록임을 다시 조회한 뒤, 에이전트가 만든 미사용 확장 테스트 항목만 교체해 재실행했다.
